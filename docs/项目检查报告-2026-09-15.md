## 七、v3 新增发现

### 🟡 F-1｜`/api/cleanup` 在默认配置下无任何调用入口（可用性缺口，非安全缺陷）

**事实**（均为实测）：

- 后端：`/api/cleanup` 已是 POST-only，且 `@_csrf_exempt` 在默认（session）模式下**不生效**
  （`utils.py:13-22`：`if _csrf is not None and AUTH_ENABLED: return _csrf.exempt(...)`，否则原样返回；全局 `CSRFProtect` 在 `app.py:88` 注册）
- 实测三种无 token 形态全部被拦：
  ```
  POST json                          → 400
  POST text/plain（跨站简单请求形态）  → 400
  POST application/x-www-form-urlencoded → 400
  POST 带首页 meta token              → 200
  ```
- 前端：`grep cleanup` 遍历 4 个 JS 模块与全部模板 → **无任何调用方**
- 文档：README:321 与操作手册:162 仅在 API 表列一行，**无调用示例**
- **延伸实测**：操作手册 §5.3 的 curl POST 示例（`:276` `/api/config`、`:293`/`:296` `/api/dual/load`）在默认配置下**全部返回 400**；
  `:292` 的注解「空body需带 Content-Type 头，否则 CSRF 保护会拦截」**是错的**——实测带 `Content-Type: application/json` 同样 400，
  决定因素是 token 而非 Content-Type

**影响**：安全上比 v1 更好（跨站 `<img>`/`<form>` 已无法触发），但照 README/手册里的 curl 直接调用写操作会拿到 400 而不知原因——
这是**文档与真实调用链之间的断层**。
