## 决策

**追认删除有效，不回滚。** 理由：

1. 项目处于开发阶段、无生产部署与外部消费者，删除的实际兼容风险为零；
2. shim 的 3 个 P1（尤其 CSRF/认证绕过）使**保留 shim 反而更危险**——删除同时消除了攻击面；
3. 内部调用为 0 有实测证据（T4 审计灰度证据）；
4. 回滚成本极低：shim 完整存在于 git `510134a`，可随时恢复（**恢复前必须先修 P1**，见下）。

## 判定流程偏差与教训

- **D2「保留 1 个版本」的删除判定流程被跳过**：删除由提交 `9254543` 直接执行，未经过判定条件核查。
- **命中计数机制先天缺陷**：deprecation tracker 计数驻留进程内（`/api/admin/deprecation-stats`），服务重启即清零，**从机制上就无法支撑跨版本判据**。若未来再引入 shim，计数必须先落盘（JSON 文件或 DB 表）再谈「观察满 1 版本」。
- 独立审计（T4 报告）与删除提交发生在同一窗口，审计发现的 P1 未被消费即被删除动作「消亡」——**流程上应先处置审计结论（修复或决策放弃），再执行结构性删除**。

## 回滚路径

若确认存在依赖旧端点的消费者：

1. `git checkout 510134a -- src/campus_ids/web_new/shim.py src/campus_ids/web_new/deprecation.py tests/test_shim.py`；
2. 在 `app.py` 重新挂载 shim 路由（`CAMPUS_IDS_ENABLE_SHIM` 开关）；
3. **强制前置**：先修复 3 个 P1——① 全部 shim POST 路由挂 `dependencies=[Write]`；② `/api/model/train` 改走 `registry.start("train")` + confirm + 产物备份；③ 移除 `model_service` 私有训练状态；
4. 重跑规格门禁与全量 pytest。
